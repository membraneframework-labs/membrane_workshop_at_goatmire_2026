# 04 · What raw audio and video look like in memory

This is a video frame, not a JPEG or a PNG but the frame itself, the way a decoder hands it over. A decoder is the program that turns compressed video back into pictures, and what it gives you is a couple of hundred thousand bytes like these. If I give you only this, you can't draw it, because nothing in here says how wide the picture is or what the bytes mean.

In this video I'll explain what raw video and raw audio look like in memory. On the video side that means frames, resolution and pixel formats. On the audio side, samples, sample rate, sample format and channels. At the end I'll show you how to get at that raw data in Membrane, an open- source multimedia framework for Elixir.

Let's start with video. A raw video stream is a series of pictures called frames, and each frame is one flat binary, the pixels one after another. They are laid out row by row from the top, left to right. So the first thing you need to know about a frame is its resolution, because the width tells you where one row ends and the next one begins. With that, you can find any pixel: skip the rows above it, then move along its row to its column.

The second thing you need is the pixel format, which says how many bytes a pixel takes and what they mean. The one everybody knows is RGB: three bytes per pixel, one for red, one for green and one for blue, each from zero to two hundred fifty-five. Here is a two by two frame: twelve bytes, three for each pixel, the first row and then the second.

But that's not what a decoder usually gives you. Decoders mostly hand you a family of formats called YUV, which store brightness and colour separately. Your eye sees fine detail much better in brightness than in colour. So you can keep brightness for every pixel and store the colour once for every block of two by two pixels, and hardly anyone notices. The most common layout is called I420, three blocks of bytes called planes: first all the brightness bytes, then the two colour planes, each a quarter of the size. On average that's one and a half bytes per pixel instead of three, so half the memory for the same picture, before any compression is involved.

Now let's do the same for audio. Sound is a wave, and raw audio is that wave measured at regular intervals. Each measurement is called a sample, and it's just a number: how far the wave is from the middle at that moment. How often you measure is the sample rate, typically forty-four thousand one hundred or forty-eight thousand times a second.

Then you need the sample format: how big each number is and how to read it. Most of the time that's sixteen-bit integers, two bytes per sample. And you need the number of channels. Stereo has two, left and right, and in memory they are usually interleaved: one sample for the left, one for the right, and so on. So one second of stereo like that, two channels, two bytes each, forty-four thousand one hundred times a second, comes to about a hundred and seventy-six kilobytes. That's far less than video, but still about ten times the size of a typical MP3.

And this is what video and audio have in common: raw data doesn't describe itself. A raw frame has no header, and neither does a block of samples. The bytes don't say how wide the picture is, whether it's RGB or I420, or how many channels the audio has. All of that has to travel next to the data, and whoever receives the bytes needs it first.

So how does this look in Membrane? In Membrane, you build a media application as a pipeline: a chain of elements, where each element does one thing with the stream and passes it on. Before any data goes from one element to the next, the element sends a stream format, which carries that description. For raw video, that's the width, the height and the pixel format. For raw audio, the sample rate, the sample format and the number of channels. Then the data follows, and every element down the line knows how to read it.

Normally you don't see the raw stage, because the Transcoder, a component that converts media from one compressed format to another, decodes and encodes inside itself. But you can ask it for raw output instead. Here is a pipeline that decodes a video compressed with VP8 and an MP3, and writes the raw bytes of both to files.

Don't worry about the syntax, that's a topic for another episode. The first element reads the video file. The video sits in a simple container called IVF, a file format that wraps the stream, so the IVF deserializer unpacks the plain VP8 stream from it. Then the Transcoder, and instead of a compressed format we ask it for raw video in I420, which is what the VP8 decoder produces anyway. And a file sink writes whatever comes out to disk, so this file is nothing but frames, one after another.

The second branch reads the MP3, and tells the source what's inside, because MP3 has no container to say so. Then a Transcoder again, asked for raw audio. Here we spell out every field: sixteen- bit samples, forty-four thousand one hundred per second, two channels. So the file comes out exactly in the format we just described. And a file sink writes the samples to a second file.

When this pipeline is done, the video file is a hundred and fifty-eight megabytes, for half a minute of video, while the VP8 file we started with is one megabyte. And to play it, we have to tell the player everything the file doesn't say. That it's raw video, its pixel format, which ffplay calls yuv420p, its size, and the frame rate. In Membrane the frame rate comes from the timestamp on every frame, but that's a topic for another episode. Then it plays. The same for the audio: the sample format, the rate and the channels.

So, a raw frame is a flat binary of pixels, read with a resolution and a pixel format. Raw audio is a run of samples, read with a sample rate, a sample format and a channel count. None of that is in the bytes themselves, so it travels alongside them, and in Membrane that's the stream format. Thanks for watching, and see you in the next episode.
